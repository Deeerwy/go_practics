# Практическое занятие №6 — Реализация защиты от CSRF/XSS. Работа с secure cookies. Бурылин Дмитрий ПИМО-01-25

## Тема и цель работы

**Тема:** Реализация защиты от CSRF/XSS. Работа с secure cookies.

**Цель:** Освоить базовые практические подходы к защите web-приложения на Go от CSRF- и
XSS-угроз, а также научиться безопасно использовать cookies для аутентификации и хранения
пользовательского состояния.

### Что такое CSRF

**CSRF (Cross-Site Request Forgery)** — атака, при которой браузер пользователя отправляет
запрос от его имени на целевой сайт без осознанного намерения самого пользователя.

Это возможно потому, что браузер автоматически прикладывает cookies к запросу, если сайт
и политика браузера это позволяют. Злоумышленник может заставить браузер авторизованного
пользователя отправить форму или запрос на сервер — и сервер воспримет его как легитимный,
поскольку в запросе будет нужная cookie сессии.

**Схема атаки:**
1. Пользователь авторизован на сайте, в браузере есть cookie сессии.
2. Злоумышленник заставляет браузер пользователя открыть вредоносную страницу.
3. Страница автоматически отправляет запрос на целевой сайт.
4. Браузер прикладывает cookie — сервер видит «авторизованный» запрос и выполняет действие.


### Что такое XSS

**XSS (Cross-Site Scripting)** — атака, при которой вредоносный JavaScript-код внедряется
в страницу, которую затем видит пользователь в браузере.

Классический сценарий:
1. Пользователь отправляет комментарий, содержащий HTML или `<script>`.
2. Сервер сохраняет текст без обработки.
3. При отображении страницы браузер интерпретирует содержимое как HTML/JavaScript.
4. Вредоносный скрипт выполняется в контексте сайта.

**Последствия:** кража cookies, подмена интерфейса, отправка действий от лица пользователя.


### Чем CSRF отличается от XSS

| Характеристика | CSRF | XSS |
|---|---|---|
| Что атакуется | Механика авторизованного запроса | Отображение данных в браузере |
| Чьё доверие эксплуатируется | Доверие **сервера** к браузеру пользователя | Доверие **браузера** к данным от сервера |
| Что делает злоумышленник | Инициирует нежелательный запрос | Внедряет вредоносный код в страницу |
| Нужен ли JavaScript | Нет | Как правило, да |

### Роль атрибутов cookie

**`HttpOnly`**
Запрещает доступ к cookie из JavaScript в браузере. Скрипт на странице не сможет прочитать
значение cookie через `document.cookie`. Это существенно снижает риск кражи сессии при XSS-атаке.

**`Secure`**
Указывает браузеру отправлять cookie только по защищённому соединению HTTPS. Предотвращает
перехват cookie при передаче данных по незащищённой сети. В локальной учебной среде установлен
в `false`, так как приложение работает по HTTP.

**`SameSite`**
Ограничивает передачу cookie в межсайтовых сценариях:
- `Strict` — cookie отправляется только при запросах с того же сайта;
- `Lax` — cookie отправляется при навигации (переходах по ссылкам), но не при межсайтовых
  POST-запросах. Используется в данном проекте;
- `None` — cookie отправляется во всех сценариях (требует `Secure: true`).

Ошибка при неверном CSRF-токене
При отправке POST /profile с неверным или отсутствующим csrf_token
(например, через Postman или curl) сервер возвращает:

invalid csrf token

## Вывод

В ходе практической работы реализовано учебное web-приложение на Go, в котором применены
следующие механизмы защиты:

Secure cookies:

Cookie сессии настроена с атрибутами HttpOnly: true и SameSite: Lax, что снижает
риск кражи сессии через XSS и ограничивает межсайтовую передачу cookie.
CSRF-защита:

При создании сессии генерируется криптографически стойкий CSRF-токен.
Токен встраивается в скрытое поле HTML-формы.
При обработке POST-запроса сервер сверяет токен из формы с токеном в хранилище.
Запросы без токена или с неверным токеном отклоняются с кодом 403 Forbidden.
Защита от XSS:

Пользовательские данные выводятся через пакет html/template, который автоматически
экранирует HTML-символы.
Ручная сборка HTML через конкатенацию строк не используется.
Реализованные механизмы демонстрируют базовый уровень защиты, который должен присутствовать
в любом web-приложении, работающем с пользовательским вводом и сессиями.

## Контрольные вопросы

1. Что такое CSRF?

CSRF (Cross-Site Request Forgery) — атака, при которой злоумышленник заставляет браузер
авторизованного пользователя отправить нежелательный запрос на целевой сервер. Браузер
автоматически прикладывает cookie сессии, и сервер воспринимает запрос как легитимный.

2. Почему наличие cookie не гарантирует, что запрос действительно инициировал пользователь?

Браузер отправляет cookies автоматически при каждом запросе к соответствующему домену,
независимо от того, с какого сайта этот запрос был инициирован. Злоумышленник может
создать страницу, которая незаметно отправит форму на целевой сайт — браузер прикрепит
cookie без каких-либо предупреждений. Таким образом, cookie лишь подтверждает, что
в браузере существует сессия, но не подтверждает осознанное намерение пользователя.

3. Что такое XSS?

XSS (Cross-Site Scripting) — атака, при которой вредоносный JavaScript-код внедряется
в HTML-страницу, отображаемую пользователем. Это происходит, когда приложение выводит
пользовательский ввод в HTML без экранирования. Браузер интерпретирует вредоносный
фрагмент как часть страницы и выполняет его.

4. Чем CSRF отличается от XSS?

CSRF эксплуатирует доверие сервера к браузеру пользователя: сервер ошибочно считает
запрос легитимным из-за наличия cookie. XSS эксплуатирует доверие браузера к данным,
полученным от сервера: браузер выполняет вредоносный код, считая его частью страницы.
CSRF атакует механику запроса, XSS атакует отображение данных.

5. Для чего нужен CSRF-токен?

CSRF-токен — это уникальное непредсказуемое значение, которое сервер генерирует для каждой
сессии и встраивает в форму. При обработке запроса сервер проверяет, совпадает ли токен
из формы с токеном в хранилище. Злоумышленник не может знать значение токена заранее,
поэтому не может сформировать корректный запрос — даже если браузер пришлёт нужную cookie.

6. Что делает атрибут HttpOnly у cookie?

HttpOnly запрещает доступ к cookie из JavaScript. Скрипты на странице не могут прочитать
её значение через document.cookie. Это снижает риск кражи cookie сессии при успешной
XSS-атаке, поскольку вредоносный скрипт не сможет получить идентификатор сессии.

7. Для чего нужен атрибут Secure?

Secure указывает браузеру отправлять cookie только по зашифрованному соединению HTTPS.
Это предотвращает перехват значения cookie при передаче данных по незащищённой сети
(например, в публичном Wi-Fi). Без этого атрибута cookie может быть перехвачена
атакующим, который наблюдает за трафиком.

8. Какую роль играет SameSite?

SameSite ограничивает сценарии, в которых браузер прикладывает cookie к запросу:

Strict — cookie отправляется только при запросах, инициированных с того же сайта;
Lax — cookie отправляется при переходах по ссылкам, но не при межсайтовых POST-запросах;
None — ограничений нет (требует Secure).
Значение Lax является базовой защитой от CSRF: злоумышленник не сможет инициировать
POST-запрос с другого сайта с прикреплённой cookie.

9. Почему нельзя вставлять пользовательский ввод в HTML через конкатенацию строк?

При конкатенации строк пользовательский ввод вставляется в HTML как есть, без какой-либо
обработки. Если ввод содержит HTML-теги или JavaScript (<script>, обработчики событий),
браузер интерпретирует их как код и выполнит. Разработчик не контролирует, что именно
окажется в строке — любой специальный символ может нарушить структуру HTML и стать
точкой входа для атаки.

10. Почему шаблоны безопаснее ручной сборки HTML?

Пакет html/template в Go автоматически экранирует специальные HTML-символы (<, >,
&, ") при подстановке данных в шаблон. Это происходит на уровне самого шаблонизатора,
без дополнительных действий со стороны разработчика. Таким образом, даже если в данных
содержится вредоносный HTML или JavaScript, браузер получит экранированный текст и
отобразит его как обычное содержимое, не выполняя как код.
