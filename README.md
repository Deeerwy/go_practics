## Зафиксированный сценарий сравнения

Для корректного сравнения REST и GraphQL выбран единый пользовательский сценарий:

- **Экран списка задач** — требуются поля `id`, `title`, `done`
- **Экран деталей задачи** — требуются поля `id`, `title`, `description`, `done`

Оба API работают с одним и тем же in-memory хранилищем (`store.Store`),
что гарантирует идентичность данных и чистоту сравнения.

## Шаг 5. Сравнение количества запросов

Для сценария «список задач → открыть детали → обновить done»:

| Шаг сценария        | REST                          | GraphQL                    |
|---------------------|-------------------------------|----------------------------|
| Список задач        | `GET /v1/tasks`               | `query { tasks { ... } }`  |
| Детали задачи       | `GET /v1/tasks/t_001`         | `query { task(id:...) }`   |
| Обновление done     | `PATCH /v1/tasks/t_001`       | `mutation { updateTask }`  |
| **Итого запросов**  | **3**                         | **3**                      |

**Вывод:** в данном сценарии количество сетевых обращений одинаково.
Преимущество GraphQL проявляется не в числе запросов, а в точности
структуры ответа — клиент получает ровно те поля, которые запросил.


## Шаг 6. Сравнение объёма данных (over-fetching)

### Экран списка задач

Экрану нужны только `id`, `title`, `done` — **3 поля**.

| API      | Поля в ответе                          | Лишние поля   |
|----------|----------------------------------------|---------------|
| REST     | `id`, `title`, `description`, `done`  | `description` |
| GraphQL  | `id`, `title`, `done`                 | —             |

REST всегда возвращает все 4 поля объекта `Task`, даже если экрану
нужны только 3. При большом количестве задач и частых обращениях
это создаёт избыточную нагрузку на сеть.

GraphQL позволяет запросить ровно нужные поля — `description`
не включается в ответ, если клиент его не запросил.

**Количественная оценка** (2 задачи в хранилище):

```bash
# REST — сохраняем ответ
curl -s http://localhost:8080/v1/tasks > rest_list.json
wc -c rest_list.json
# → ~160 байт (4 поля × 2 объекта)

# GraphQL — запрашиваем только 3 поля
curl -s -X POST http://localhost:8080/query \
  -H "Content-Type: application/json" \
  -d '{"query":"{ tasks { id title done } }"}' > gql_list.json
wc -c gql_list.json
# → ~120 байт (3 поля × 2 объекта)
```

На малом объёме разница незначительна, но при сотнях полей и тысячах
объектов экономия становится существенной.

## Шаг 7. Сравнение обработки ошибок

### REST — запрос несуществующей задачи

```bash
curl -s -v http://localhost:8080/v1/tasks/unknown | jq
```

Ответ:
```
HTTP/1.1 404 Not Found
Content-Type: application/json
```
```json
{ "error": "task not found" }
```

Клиент однозначно понимает ошибку по HTTP-статусу `404`.
Мониторинг и логирование работают стандартно — достаточно
отслеживать коды ответов на уровне инфраструктуры.

### GraphQL — запрос несуществующей задачи

```graphql
query {
  task(id: "unknown") {
    id
    title
    done
  }
}
```

Ответ (HTTP 200):
```json
{
  "data": {
    "task": null
  }
}
```

В текущей реализации резолвер возвращает `null` без ошибки —
клиент должен проверять не HTTP-статус, а наличие данных в `data`.

### GraphQL — ошибка авторизации при мутации

```graphql
mutation {
  createTask(input: { title: "Test" }) {
    id
  }
}
```

Ответ (HTTP 200):
```json
{
  "errors": [
    {
      "message": "unauthorized",
      "path": ["createTask"]
    }
  ],
  "data": null
}
```

| Аспект               | REST                          | GraphQL                          |
|----------------------|-------------------------------|----------------------------------|
| Признак ошибки       | HTTP-статус (4xx, 5xx)        | Поле `errors` в теле ответа      |
| HTTP-статус при ошибке | Соответствует ошибке        | Чаще всего `200 OK`              |
| Простота анализа     | Высокая — стандарт HTTP       | Ниже — нужно парсить тело        |
| Мониторинг           | По кодам ответов              | Требует анализа тела запроса     |

## Шаг 8. Сравнение документирования и тестирования

| Аспект               | REST                                  | GraphQL                              |
|----------------------|---------------------------------------|--------------------------------------|
| Документация         | Swagger/OpenAPI, отдельный файл       | Самодокументируемая схема (SDL)      |
| Тестирование         | curl, Postman — интуитивно            | Playground, curl с JSON-телом        |
| Точка входа          | Несколько URL (`/v1/tasks`, `/v1/...`)| Один endpoint (`/query`)             |
| Изучение API         | Достаточно знать HTTP-методы          | Нужно понимать типы, query, mutation |
| Воспроизведение      | Прямая вставка curl в терминал        | Требует формирования JSON с query    |

В учебном контексте REST оказался проще для первичного тестирования:
команды curl читаются интуитивно, HTTP-методы (`GET`, `POST`, `PATCH`)
сразу передают намерение. GraphQL Playground удобен для интерактивной
работы, но требует предварительного изучения синтаксиса запросов.

## Шаг 9. Сравнение кэширования (концептуально)

**REST** — кэширование естественно вписывается в HTTP-модель:

- Каждый ресурс имеет уникальный URL (`/v1/tasks/t_001`)
- Браузеры, прокси и CDN кэшируют `GET`-запросы по URL автоматически
- Заголовки `Cache-Control`, `ETag`, `Last-Modified` работают из коробки

**GraphQL** — кэширование усложняется:

- Все запросы идут на один endpoint `/query` методом `POST`
- Стандартный HTTP-кэш не различает разные запросы на одном URL
- Решения: **persisted queries** (кэш по хешу запроса),
  кэширование на уровне данных (DataLoader), клиентский кэш
  (Apollo Client, urql)

**Вывод:** для сценариев с интенсивным чтением и требованиями к
производительности REST даёт кэширование «бесплатно». GraphQL
требует дополнительной инфраструктуры для достижения того же эффекта.

### Итого:

Проведённое сравнение показало, что REST и GraphQL решают одну и ту же задачу — предоставление доступа к сущности `Task` — принципиально разными способами, каждый из которых имеет свою область применения. В рамках выбранного сценария (список задач, детали задачи, создание и обновление) количество сетевых обращений оказалось одинаковым для обоих подходов — по три запроса. Это подтверждает важный тезис: GraphQL не сокращает число запросов автоматически, его ключевое преимущество состоит в точности структуры ответа.

Наиболее ощутимое различие проявилось при получении списка задач. REST вернул все четыре поля объекта `Task`, включая `description`, которое экрану списка не нужно. GraphQL позволил запросить только `id`, `title` и `done`, исключив лишнее поле. В реальных системах с большим числом полей и высокой нагрузкой этот эффект становится значимым — снижается объём трафика и нагрузка на клиентское приложение.

В части обработки ошибок REST оказался более прозрачным: HTTP-статусы `404`, `400`, `401` однозначно сигнализируют о характере проблемы без разбора тела ответа. В GraphQL ошибки возвращаются внутри JSON при HTTP `200`, что усложняет мониторинг и требует дополнительной логики на стороне клиента и в системах наблюдаемости.

Кэширование остаётся явным преимуществом REST: уникальные URL и стандартные GET-запросы позволяют использовать браузерный кэш, CDN и прокси без дополнительной настройки. GraphQL с единым endpoint `/query` и POST-методом требует специализированных решений — persisted queries или клиентского кэша уровня Apollo.

С точки зрения документирования и тестирования оба подхода удобны, но по-разному. REST-запросы воспроизводятся через curl интуитивно, а документация формируется через Swagger/OpenAPI. GraphQL предоставляет самодокументируемую схему и интерактивный Playground, однако требует знакомства с синтаксисом запросов и системой типов.

Итоговый вывод: для учебного CRUD-сервиса с простой моделью данных и небольшим числом экранов REST является более практичным выбором — он проще в реализации, тестировании и мониторинге. GraphQL оправдывает свою сложность в системах с разнообразными клиентами (веб, мобильный), большим числом полей в модели и требованиями к точному контролю над структурой ответа. Выбор между подходами должен определяться не популярностью технологии, а конкретными требованиями проекта.


## Контрольные вопросы

**1. В чём принципиальное отличие REST и GraphQL?**

REST строится вокруг множества URL-ресурсов и HTTP-методов: каждый endpoint соответствует определённому ресурсу, а метод (`GET`, `POST`, `PATCH`, `DELETE`) определяет операцию. Структура ответа фиксирована на стороне сервера. GraphQL использует единую точку входа (`/query`), а клиент сам формирует запрос и указывает, какие поля ему нужны. Сервер возвращает ровно ту структуру, которую запросил клиент.

---

**2. Что такое over-fetching и under-fetching?**

**Over-fetching** — клиент получает больше данных, чем нужно. Например, экран списка задач запрашивает `GET /v1/tasks` и получает все поля, включая `description`, хотя отображает только `id`, `title`, `done`.

**Under-fetching** — одного запроса недостаточно для получения всех нужных данных. Например, клиент получает список задач, а затем вынужден делать отдельный запрос для каждой задачи, чтобы получить детали, — возникает серия последовательных обращений (проблема N+1).

---

**3. Почему GraphQL позволяет клиенту точнее выбирать поля ответа?**

Потому что структура запроса формируется на стороне клиента, а не жёстко задаётся сервером. Клиент явно перечисляет нужные поля в теле запроса, и резолвер возвращает только их. Сервер не принимает решение о том, какие данные нужны клиенту, — это определяет сам клиент при каждом запросе.

---

**4. Почему REST проще кэшировать стандартными средствами HTTP?**

В REST каждый ресурс имеет уникальный URL (`/v1/tasks/t_001`), а операции чтения используют метод `GET`. Браузеры, прокси-серверы и CDN умеют кэшировать GET-запросы по URL с учётом заголовков `Cache-Control`, `ETag` и `Last-Modified` без дополнительной настройки. В GraphQL все запросы идут на один URL методом `POST`, поэтому стандартный HTTP-кэш не может их различить — требуются специализированные решения.

---

**5. Чем отличается обработка ошибок в REST и GraphQL?**

В REST ошибки выражаются через HTTP-статус-коды: `404 Not Found`, `400 Bad Request`, `401 Unauthorized`, `500 Internal Server Error`. Клиент и инфраструктура (мониторинг, логи) понимают характер ошибки по коду без разбора тела ответа.

В GraphQL сервер почти всегда возвращает `HTTP 200 OK`, даже при ошибке. Сама ошибка передаётся внутри JSON в поле `errors`. Это требует от клиента дополнительной логики разбора тела ответа и усложняет стандартный мониторинг.

---

**6. В каких случаях REST оказывается более практичным решением?**

REST предпочтителен когда:
- проект представляет собой простой CRUD-сервис с небольшим числом сущностей;
- все клиенты используют одинаковый набор полей;
- важно простое кэширование на уровне HTTP;
- команда небольшая и важна скорость разработки;
- необходима простая интеграция со сторонними системами через стандартный HTTP;
- проект является внутренним административным сервисом.

---

**7. В каких случаях GraphQL может дать преимущества?**

GraphQL выгоден когда:
- существуют разные типы клиентов (веб, мобильный, IoT) с разными потребностями в данных;
- модель данных содержит много полей, и разные экраны используют разные их подмножества;
- важно минимизировать трафик (мобильные сети с ограниченной пропускной способностью);
- необходимо объединить данные из нескольких источников в одном запросе;
- команда готова инвестировать в настройку схемы, резолверов и инфраструктуры кэширования.

---

**8. Почему корректное сравнение REST и GraphQL нужно проводить на одном и том же сценарии?**

Потому что преимущества и недостатки каждого подхода проявляются по-разному в зависимости от сценария. Если сравнивать разные сущности, разные объёмы данных или разные паттерны доступа, вывод будет некорректным — он будет отражать различие в сценариях, а не в технологиях. Только при фиксированном сценарии можно честно оценить, какой подход требует меньше запросов, возвращает меньше лишних данных и удобнее для конкретного типа клиента.

---

**9. Какие сложности возникают при сопровождении GraphQL API?**

- Необходимо поддерживать схему (SDL) и синхронизировать её с резолверами
- При изменении схемы нужно проверять обратную совместимость для всех клиентов
- Мониторинг и логирование сложнее — ошибки скрыты внутри HTTP 200
- Кэширование требует дополнительных инструментов (persisted queries, DataLoader)
- Производительность труднее контролировать: клиент может запросить произвольно сложную вложенную структуру, что нагружает сервер
- Документация и типизация требуют поддержания актуальной схемы

---

**10. Почему для учебных CRUD-сервисов REST часто оказывается проще?**

Учебный CRUD-сервис обычно имеет небольшое число сущностей, простую модель данных и единственный тип клиента. В таких условиях гибкость GraphQL (выбор полей, объединение запросов) не даёт ощутимого преимущества, а его накладные расходы — схема, резолверы, настройка генератора, JWT в отдельном middleware — создают избыточную сложность. REST решает ту же задачу предсказуемее: маршруты соответствуют ресурсам, HTTP-методы передают намерение, curl позволяет тестировать без дополнительных инструментов. Порог входа ниже, а результат достигается быстрее.
```
