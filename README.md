### 1. Поднять RabbitMQ локально через docker-compose

Файл deploy/rabbit/docker-compose.yml запускает RabbitMQ с Management UI:

    version: "3.9"
    services:
      rabbitmq:
        image: rabbitmq:3-management
        container_name: pz13-rabbitmq
        ports:
          - "5672:5672"
          - "15672:15672"
        environment:
          RABBITMQ_DEFAULT_USER: guest
          RABBITMQ_DEFAULT_PASS: guest

Команды запуска:

    cd deploy/rabbit
    docker compose up -d
    docker compose ps

Management UI доступен по адресу http://localhost:15672

### 2. Создать очередь task_events

Очередь объявляется в момент запуска сервиса tasks и worker.
Оба компонента вызывают QueueDeclare с одинаковыми параметрами.

Параметры очереди:

    Имя:        task_events
    Durable:    true   
    AutoDelete: false
    Exclusive:  false

Объявление в publisher:

    _, err := ch.QueueDeclare(
        queueName,
        true,
        false,
        false,
        false,
        nil,
    )

После запуска сервисов очередь появится в Management UI на вкладке Queues.
В колонке Features будет отображаться буква D, что означает durable.


### 3. Реализовать публикацию события task.created

Формат события в JSON:

    {
      "event": "task.created",
      "task_id": "t_pz13-001",
      "ts": "2026-05-17T11:25:47Z",
      "request_id": "pz13-001",
      "producer": "tasks-service",
      "version": "1"
    }

Обязательные поля: event, task_id, ts.
Дополнительные поля: request_id, producer, version.

Сообщение публикуется с DeliveryMode = Persistent, чтобы RabbitMQ
сохранял его на диске и не терял при сбое.

Публикация происходит строго после успешного создания задачи.
Это гарантирует, что worker не получит событие о несуществующей задаче.

Выбранный режим публикации: best effort.
При ошибке публикации задача считается созданной,
ошибка только логируется, клиент получает HTTP 201.


### 4. Реализовать отдельный worker для получения сообщений

Worker — это самостоятельный процесс в services/worker.
Он не связан с HTTP-сервером и запускается независимо.

Порядок работы worker:

    1. Подключается к RabbitMQ
    2. Объявляет очередь task_events с теми же параметрами, что и producer
    3. Устанавливает prefetch
    4. Подписывается на сообщения из очереди
    5. Для каждого сообщения: десериализует JSON, логирует событие, отправляет ack

Пример лога worker после получения события:

    [worker] received event=task.created task_id=t_pz13-001 ts=2026-05-17T11:25:47Z request_id=pz13-001 producer=tasks-service


### 5. Настроить ручное подтверждение обработки через ack

Worker подписывается на очередь с параметром autoAck = false.
Это означает, что подтверждение отправляется вручную после обработки.

Логика подтверждения:

    Сообщение успешно обработано  ->  d.Ack(false)
    Сообщение не удалось разобрать ->  d.Nack(false, false)

При вызове Ack брокер считает сообщение обработанным и удаляет его из очереди.
При вызове Nack с requeue = false невалидное сообщение отбрасывается без повтора.

Пока worker не отправил ack, сообщение остаётся в состоянии Unacked.
Это видно в Management UI в колонке Unacked на вкладке Queues.


### 6. Использовать prefetch

Worker устанавливает prefetch = 1 через вызов ch.Qos:

    ch.Qos(1, 0, false)

Это означает, что брокер не отдаст worker следующее сообщение,
пока тот не подтвердит обработку текущего через ack.

Значение 1 выбрано намеренно: в учебном сценарии важно явно контролировать
каждый шаг обработки и убедиться, что ack работает корректно.
В продакшене prefetch можно увеличить до 5 или 10 для повышения пропускной способности.

## Контрольные вопросы

1. Зачем нужен брокер сообщений, если между сервисами можно использовать HTTP?

HTTP — синхронный протокол: отправитель блокируется и ждёт ответа.
Если получатель недоступен, запрос падает с ошибкой.
Брокер сообщений решает эту проблему: отправитель публикует сообщение в очередь
и сразу получает управление обратно. Получатель обработает сообщение позже,
когда будет готов. Это позволяет разделить компоненты по времени и по нагрузке,
повысить отказоустойчивость и масштабировать обработчики независимо от API.

2. Что такое producer и consumer?

Producer — компонент, который публикует сообщения в очередь.
В данной работе producer — сервис tasks, который после создания задачи
отправляет событие task.created в очередь task_events.

Consumer — компонент, который читает сообщения из очереди и обрабатывает их.
В данной работе consumer — worker-процесс, который получает событие,
логирует его и подтверждает обработку через ack.

3. Почему сообщение нужно публиковать только после успешного создания задачи?

Если опубликовать событие до создания задачи, а создание потом упадёт с ошибкой,
worker получит событие о задаче, которой не существует.
Это приведёт к рассинхронизации данных между сервисами.
Публикация после успеха гарантирует, что событие соответствует реальному состоянию системы.

4. Что такое ack и зачем он нужен?

Ack (acknowledgement) — подтверждение обработки сообщения.
Когда worker успешно обработал сообщение, он вызывает Ack.
После этого брокер считает сообщение доставленным и удаляет его из очереди.
Без ack сообщение остаётся в состоянии Unacked и может быть доставлено повторно.
Это защищает от потери сообщений при сбоях в процессе обработки.

5. Почему возможна повторная доставка сообщения?

Если worker получил сообщение, начал обработку, но упал до отправки ack,
брокер не получил подтверждения. С точки зрения RabbitMQ сообщение не обработано.
После восстановления соединения или перезапуска worker брокер доставит его снова.
Поэтому обработчики сообщений нужно проектировать идемпотентными:
повторная обработка одного и того же сообщения не должна вызывать проблем.

6. Что делает параметр prefetch?

Prefetch ограничивает число сообщений, которые брокер может одновременно
передать одному consumer без получения ack.
При prefetch = 1 worker получает следующее сообщение только после того,
как подтвердит обработку текущего. Это предотвращает ситуацию, когда медленный
worker забирает из очереди больше сообщений, чем успевает обработать,
и позволяет равномерно распределять нагрузку между несколькими worker-процессами.

7. Чем durable queue отличается от non-durable queue?

Durable queue сохраняется на диске и переживает перезапуск RabbitMQ.
После перезапуска брокера очередь и все persistent-сообщения в ней будут восстановлены.

Non-durable queue существует только в памяти.
При остановке или перезапуске брокера она и все её сообщения будут удалены.

В данной работе используется durable queue для повышения надёжности.

8. Почему JSON удобен как учебный формат сообщения?

JSON удобен по нескольким причинам:
- Читаем визуально: сообщение можно прочитать прямо в логах или в Management UI
- Легко сериализуется в Go через стандартный пакет encoding/json
- Не требует отдельных схем или кодогенерации, в отличие от Protobuf или Avro
- Естественно продолжает стиль проекта, где уже используются JSON-запросы и ответы

9. Что означает режим best effort при публикации события?

Best effort означает, что ошибка публикации события не считается критической.
Задача создаётся и считается успешной независимо от того, удалось ли опубликовать событие.
При ошибке публикации она только логируется, а клиент получает HTTP 201.

Этот режим выбран потому, что создание задачи — основная операция,
и она не должна зависеть от доступности брокера.
Worker выполняет вспомогательную роль, поэтому временная потеря события допустима.

Альтернатива — strict-режим, при котором ошибка публикации возвращает клиенту HTTP 500.
Он уместен, когда событие критично и его потеря недопустима.

10. Почему worker лучше выносить в отдельный процесс, а не смешивать с HTTP-обработчиками?

Если запустить consumer внутри HTTP-сервера, возникают несколько проблем:
- Бесконечный цикл чтения сообщений блокирует горутину и усложняет управление жизненным циклом
- HTTP-сервер и worker начинают конкурировать за ресурсы одного процесса
- Невозможно масштабировать их независимо: нельзя запустить 3 worker и 1 HTTP-сервер
- При сбое в обработке сообщений падает весь сервис вместе с API

Отдельный процесс решает все эти проблемы: worker масштабируется независимо,
перезапускается без влияния на API и имеет собственный жизненный цикл.
