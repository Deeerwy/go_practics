# Практическое занятие №11 — GraphQL API с использованием gqlgen. Бурылин Дмитрий ПИМО-01-25

## Описание проекта

GraphQL API для управления задачами (Task), реализованный на языке Go
с использованием библиотеки gqlgen. Поддерживает операции чтения,
создания, обновления и удаления задач, а также упрощённую JWT-авторизацию
для мутаций.


## Стек технологий

- Go 1.25
- github.com/99designs/gqlgen v0.17.90
- In-memory хранилище (без БД)
- JWT-авторизация через заголовок Authorization

## GraphQL-схема

```graphql
type Task {
  id: ID!
  title: String!
  description: String
  done: Boolean!
}

type Query {
  tasks: [Task!]!
  task(id: ID!): Task
}

type Mutation {
  createTask(input: CreateTaskInput!): Task!
  updateTask(id: ID!, input: UpdateTaskInput!): Task!
  deleteTask(id: ID!): Boolean!
}

input CreateTaskInput {
  title: String!
  description: String
}

input UpdateTaskInput {
  title: String
  description: String
  done: Boolean
}
```

## Авторизация

В проекте реализована упрощённая JWT-авторизация.
Проверка токена выполняется только в мутациях.
Запросы (Query) доступны без авторизации.

Чтобы выполнить мутацию, необходимо передать заголовок:

```
Authorization: Bearer my-test-token-123
```

В GraphQL Playground заголовок добавляется во вкладке Headers:

```json
{
  "Authorization": "Bearer my-test-token-123"
}
```
![7](./screens/image-6.png)

Если токен не передан, сервер вернёт ошибку:

```json
{
  "errors": [
    {
      "message": "unauthorized: токен не предоставлен или недействителен"
    }
  ]
}
```
![8](./screens/image-7.png)

В продакшен-версии токен должен быть верифицирован криптографически
с проверкой подписи и срока действия. В учебной версии любая непустая
строка после Bearer считается валидным токеном.

## Ответы на контрольные вопросы

### 1. Что такое GraphQL и в чём его основное отличие от REST API?

GraphQL — это язык запросов к API и среда выполнения этих запросов
на стороне сервера. Клиент сам описывает, какие поля и в какой структуре
он хочет получить, отправляя запрос на единственный endpoint.

Отличие от REST:
- В REST для каждого ресурса существует отдельный endpoint (/tasks, /users).
  Сервер сам решает, какие данные вернуть, и клиент не может изменить состав ответа.
- В GraphQL endpoint один (/query), а клиент в теле запроса указывает
  нужные поля. Это устраняет over-fetching (лишние данные) и under-fetching
  (необходимость делать несколько запросов).

### 2. Для чего используется GraphQL-схема?

Схема — это центральный контракт между клиентом и сервером.
Она описывает:
- типы данных (type Task, type User и т.д.),
- доступные операции чтения (type Query),
- доступные операции изменения (type Mutation),
- входные параметры (input CreateTaskInput).

На основе схемы gqlgen генерирует Go-код: модели, интерфейсы и заготовки
резолверов. Клиент использует схему для формирования корректных запросов.

### 3. Чем Query отличается от Mutation?

Query — операции чтения данных. Они не изменяют состояние системы.
Примеры: получить список задач, получить задачу по ID.

Mutation — операции изменения данных. Они создают, обновляют или удаляют
записи. Примеры: createTask, updateTask, deleteTask.

Разделение логически отделяет операции чтения от модификации,
что делает API более понятным и предсказуемым.

### 4. Что такое резолвер и какую роль он выполняет?

Резолвер — это функция на стороне сервера, которая фактически выполняет
GraphQL-операцию. Каждый запрос или мутация из схемы имеет соответствующий
резолвер в коде.

Резолвер связывает GraphQL-схему с реальной логикой приложения:
обращается к базе данных, сервисному слою, выполняет валидацию,
формирует и возвращает ответ клиенту.

Например, резолвер Tasks возвращает список задач из хранилища,
а резолвер CreateTask создаёт новую запись и возвращает её клиенту.

### 5. Почему GraphQL позволяет уменьшить over-fetching данных?

В REST сервер всегда возвращает фиксированный набор полей, даже если
клиенту нужны только два из десяти. Это и есть over-fetching.

В GraphQL клиент явно перечисляет нужные поля прямо в запросе:

```graphql
query {
  tasks {
    id
    title
  }
}
```

Сервер вернёт только id и title, даже если у задачи есть ещё
description, done и другие поля. Лишние данные по сети не передаются.

### 6. Для чего используется библиотека gqlgen в Go-проекте?

gqlgen — это инструмент для создания GraphQL-серверов на Go.
Его особенность в подходе schema-first: разработчик сначала описывает
схему в файле schema.graphqls, затем запускает генерацию.

gqlgen автоматически создаёт:
- Go-структуры для типов схемы (model/models_gen.go),
- интерфейсы резолверов,
- HTTP-обработчик GraphQL-сервера (generated.go).

Разработчику остаётся только реализовать бизнес-логику в резолверах,
не тратя время на написание рутинного инфраструктурного кода.

### 7. Почему желательно использовать общий сервисный слой для REST и GraphQL?

Если в проекте есть и REST, и GraphQL, дублировать бизнес-логику
в каждом слое — плохая практика. Это увеличивает количество кода,
усложняет сопровождение и создаёт риск расхождения в поведении.

Правильный подход: и REST-обработчики, и GraphQL-резолверы вызывают
одни и те же методы сервисного слоя. Бизнес-логика реализована один раз,
а GraphQL и REST — это просто два разных транспортных протокола
поверх одной и той же логики.

### 8. Что произойдёт, если GraphQL-запрос попросит слишком большой объём данных?

GraphQL по умолчанию не ограничивает сложность или глубину запросов.
Если клиент запросит очень глубоко вложенную структуру или огромное
количество данных, сервер будет выполнять запрос до конца,
что может привести к высокой нагрузке и деградации производительности.

Для защиты от таких ситуаций используются:
- ограничение глубины запроса (query depth limit),
- ограничение сложности запроса (query complexity limit),
- пагинация результатов,
- таймауты на уровне HTTP-сервера.

В gqlgen эти ограничения можно настроить через обработчики
graphql/handler.

### 9. Какие преимущества даёт Playground при тестировании API?

GraphQL Playground — это встроенный браузерный интерфейс для работы с API.

Его преимущества:
- интерактивное выполнение запросов и мутаций прямо в браузере без
  дополнительных инструментов,
- автодополнение полей на основе схемы,
- встроенная документация по всем типам, запросам и мутациям,
- поддержка переменных (вкладка Variables) и заголовков (вкладка Headers),
- мгновенный просмотр ответа сервера в удобном JSON-формате.

### 10. В каких случаях GraphQL особенно удобен на практике?

GraphQL особенно полезен в следующих ситуациях:

- Мобильные приложения, где важно минимизировать объём передаваемых данных
  и количество сетевых запросов из-за ограниченного канала связи.

- Фронтенд с разными представлениями одних данных, когда разным экранам
  нужен разный состав полей одного и того же ресурса.

- Быстро меняющийся продукт, где API часто дорабатывается: GraphQL позволяет
  добавлять поля без версионирования и без риска сломать существующих клиентов.

- Агрегация нескольких источников данных в единый ответ, когда за одним
  запросом стоят данные из разных сервисов или таблиц.

- Публичные API для сторонних разработчиков, которым важна гибкость
  выборки данных без необходимости согласовывать формат ответа с командой бэкенда.
